근거: [결정반영 PLAN](2026-10-10_결정반영_PLAN.md), [DECISIONS 2026-10-10](../records/decisions/DECISIONS.md). 커밋·원격 DB 명령 없음.

## 1. 추구미 Chip 선택
- **무엇을**: `POST /recommendations` 본문에 `aesthetic_id`(uuid|null, 생략=메인)를 받는다. 사용자 선호(메인·보조)에 없으면 422(예약 전 검증, DB도 `invalid_recommendation`으로 재검증). 엔진 가중치를 role 기반으로 바꿨다: Chip 0.6, 그 외 메인 0.25, 보조 0.15(저장된 weight는 쓰지 않음). 선택값은 요청 해시·`reason_facts`(`selected_aesthetic:<id>`)·새 컬럼 `recommendation_requests.selected_aesthetic_id`에 남고 응답 `selected_aesthetic_id`로 나간다. 엔진·규칙 버전을 `deterministic-g10-v1`/`weather-category-aesthetic-g10-v1`로 올렸다. TPO는 그대로 null만 허용(OpenAPI에 deprecated 표시).
- **왜**: 홈 Chip 0~2 결정. 기존 엔진은 weight만 써서 메인·보조 구분과 Chip 선택을 반영하지 못했다.
- **DB**: `202610100003_reco_weather_stats.sql` — 컬럼 추가, 8인자 `begin_my_recommendation`를 DROP하고 9인자(`p_selected_aesthetic_id`) 하나만 둔다(본문은 202610010002판 + Chip 검증·컬럼 기록). 원격 DB가 아직 push 전이라 구판 호환이 필요 없고, 오버로드는 PostgREST 함수 선택 모호성 위험이 있어 코디네이터 요청으로 단일화했다. `supabase/tests/recommendations.sql` 호출 8곳에 `null` 인자를 더했다. 교차 검토 반영으로 Chip 검증은 멱등 재생 판단 뒤(새 예약 직전)로 옮겨, 같은 키 재시도는 그사이 선호가 바뀌어도 이전 결과를 돌려준다.

## 2. 옷장 충분·부족
- **무엇을**: 기준을 카테고리 무관 2벌 이상으로 바꿨다. 2벌 미만이면 `insufficient_wardrobe`(추천 0개). 2벌 이상이면 상의·하의 중 가진 축으로 조합하고(둘 다 없으면 다른 첫 카테고리), 신발·18도 미만 아우터를 덧붙이며, 한 벌짜리면 가방·액세서리를 하나 더한다. 같은 옷 조합은 중복 제거. 끝내 옷 1개뿐인 조합은 추천하지 않는다(교차 검토 반영: 가방 2개·상의 2개처럼 같은 카테고리 2벌뿐이면 추천 0개 → `insufficient_wardrobe` + `missing_category:*`).
- **사유 코드**(`shortfall_reasons`): `insufficient_wardrobe`, `missing_category:<카테고리>`(상의·하의·신발 + 10도 미만 아우터), `requested_count_not_reached`. 응답에 `missing_categories` 배열을 파생해 추가했다. 구 코드 `missing_complete_base_outfit`은 더 만들지 않고, 구 저장 행은 그대로 읽히며 `missing_categories`는 []다.
- **왜**: '상의+하의 완성 코디 필수' 규칙이 결정(2벌 이상·하의 없어도 조합·3개 미만 허용)과 맞지 않았다. 사유를 기존 `shortfall_reasons` 배열에 담아 `store_recommendation` RPC를 바꾸지 않았다.

## 3. 지역 직접 선택
- **무엇을**: `lib/weather.js`에 시·도 17개 코드(`seoul`…`jeju`)와 시청·도청 소재지 부근 근사 좌표 상수(주석에 출처·근사 명시)를 두었다. `GET /weather/current?region_code=seoul`, 추천 `location: { region_code }`를 받는다. lat+lon과 region_code는 정확히 하나만; 둘 다 없음·둘 다 있음·모르는 코드는 422 `VALIDATION_ERROR`.
- **왜**: 위치 권한 거절 시 지역 직접 선택 결정. 스키마 변경 없이 같은 격자 캐시를 재사용한다.

## 4. 통계 최다 추구미
- **무엇을**: `get_my_closet_statistics()`를 같은 시그니처로 교체해 `aesthetic_totals`(추구미별 점수 합 내림차순, 동점 code 순)와 `top_aesthetic`(없으면 null)을 더했다. 착용(worn)·오늘 이전 OOTD **건마다** 스냅샷의 서로 다른 옷의 `garment_aesthetic_scores`를 합산하므로 하루 여러 건이면 건별로 더해진다. API 투영은 `lib/outfits.js`의 `closetStatisticsResponse`만 최소 수정(트랙 B 파일, 함수 하나 + 보조 함수 하나 추가).

## 미검증·남은 위험
- hosted Supabase·PostgREST에서 9인자 `begin_my_recommendation` 호출은 원격 스모크 전 미검증.
- 대표 좌표는 근사값이며 같은 시·도 안 실제 날씨와 다를 수 있다. 엔진 가중치(0.6/0.25/0.15)·부족 부위 범위(신발 포함, 아우터 10도 미만)는 우리 쪽 임의 기준이라 PM 확인 대상.
- 추천 재현성: 구 요청 키를 같은 본문으로 재시도해도 엔진 버전이 바뀌어 해시가 달라지므로 배포 직후 진행 중 재시도는 `IDEMPOTENCY_CONFLICT`가 날 수 있다.
