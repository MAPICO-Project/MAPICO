# 2026-10-10 트랙 A 피드·따라입기 결과

근거: [결정 반영 계획](2026-10-10_결정반영_PLAN.md), [DECISIONS 2026-10-10](../records/decisions/DECISIONS.md). 원격 DB push·커밋 없음.

## 1. 포스트↔옷 연결
- **무엇을**: `feed_post_items` 추가(migration `202610100001_feed_links_mimic.sql`). 포스트당 작성자 본인 옷 1~10개, `position` 순서, 포스트 삭제 시 CASCADE. `create_my_feed_post`·`update_my_feed_post`에 `p_garment_ids`(수정은 `p_has_garment_ids`) 추가(구 시그니처 drop). `source_ootd_id`만 주면 그 OOTD의 아직 쓸 수 있는 옷을 자동 연결. 기존 OOTD 출처 포스트는 migration에서 같은 방식으로 백필.
- **왜**: 유저플로우 "디지털 옷장 아이템 최소 1개 연결 필수"와 따라입기 재설계의 입력.
- **보장**: RPC 검증(0개·중복·11개 이상 422, 남의 옷 404 `GARMENT_NOT_FOUND`, 삭제·미검증 옷 409, OOTD에 쓸 수 있는 옷이 없으면 409) + DB 보장(복합 FK `(user_id, garment_id)`로 남의 옷 불가, deferred constraint trigger로 커밋 시점 1개 이상: 포스트 insert·public 전환·링크 삭제 시 검사). 연결 없는 구 포스트는 숨김·삭제는 되지만 다시 공개할 수 없다(`invalid_feed_state` → 409 `FEED_CONFLICT`).
- **공개 표현**: 연결 시점 스냅샷(category·color_hex·pattern·추구미 점수)을 저장하고, 공개 DTO `linked_items`에는 `{id(연결 행 ID), position, category}`만 낸다. 작성자 `garment_id`·옷장 이미지(`garment_assets`, closet-private)·색·패턴은 내보내지 않는다(서비스 전용 `project_feed_posts`에서만 조립, 기존 feed_media 패턴과 동일). 원본 옷을 하드 삭제하면 `garment_id`만 NULL(`on delete set null (garment_id)`, PG15+ 문법)이고 스냅샷·게시물은 유지된다. 소프트 삭제는 링크에 영향 없음.
- **아이템 이미지**: 이번에 구현하지 않음. 필요하면 feed_media처럼 작성자가 명시적으로 올리는 공개용 복사본(`feed-private` 버킷, 서명 URL)으로 해야 하며, 옷장 cutout을 서버가 자동 복사하는 방식은 불변조건 위반이라 쓰지 않는다. PM 협의 대상.

## 2. 따라입기 재설계
- **무엇을**: `create_my_mimic_job`이 포스트 연결 아이템 ↔ 내 옷장을 SQL에서 동기 매칭하고 바로 succeeded/no_match로 끝낸다. `POST /mimic-jobs`(202)·`GET /mimic-jobs/{jobId}` 인터페이스 유지.
- **매처 rule-v1**: 같은 카테고리 필수. 점수 = 색 0.4(RGB 거리) + 패턴 0.3(같으면 1, 다르면 0) + 추구미 0.3(점수 벡터 코사인). 속성을 모르면 0.3(약한 근거). 0.2 미만은 미매칭. 옷장 아이템 하나는 한 번만 배정(점수 내림차순 greedy) → 결과 garment_ids를 그대로 `POST /saved-outfits`에 넣을 수 있다(기존 보관함 흐름 유지).
- **AI 자리**: `garment_embeddings`(옷당 1벡터, service-only, 계정 삭제 시 CASCADE). 원본 옷과 후보 옷이 같은 `model_version` 벡터를 가지면 점수 = 0.5·rule + 0.5·max(cos,0), `model_version='rule-v1-vector'`. 지금은 채우는 worker가 없다.
- **대표 이미지 재분석 경로 비활성**: `claim_mimic_job`은 항상 null(시그니처·권한 유지), 열린 구 작업은 `LEGACY_PIPELINE_RETIRED`로 실패 처리(응답은 `MIMIC_FAILED`). 이유: 결정이 재분석을 폐기했고, 큐에 남으면 worker가 공개 이미지를 다시 분석하게 된다. callback(`lib/mimic-callback.js`, `apply_mimic_result`)은 코드 변경 없이 남겨 두었고 리스 가진 작업이 없으므로 사실상 휴면. AI가 붙을 때는 임베딩 적재가 우선 경로.
- 구 데이터 없음(원격 DB 비어 있음). 연결 없는 구 공개 포스트가 생기면 비공개 전환 후 재연결한다(공개 상태에서는 캡션 수정도 409).
- 연결 없는 구 포스트로 따라입기 → 409 `MIMIC_CONFLICT`(기존 `feed_media_unavailable` 메시지 재사용, `lib/supabase-user.js` 미수정).

## 3. 결과 등급
- 아이템 `grade`: 내부 점수 ≥ 0.75 high, ≥ 0.5 medium, 그 미만 low, 미매칭 null. 전체 `grade`: 연결 아이템 전체 점수 평균(미매칭 0)에 같은 임계값, succeeded에서만. 임계값 정본은 SQL `g10_mimic_grade`.
- 교차 검토 반영: 숫자 `similarity`는 응답(RPC·API 모두)에서 뺐다. 아이템별 숫자로 남의 옷 속성(색·패턴)을 추정할 수 있기 때문. 점수는 `mimic_requests.result`에만 남는다. coverage·no_match 처리 유지.
- 매치에 `post_item_id`(= `linked_items[].id`), `category` 추가. 구 이미지 기반 결과는 둘 다 null로 계속 읽힌다.

## 미검증·남은 위험
- hosted Supabase 미적용. `on delete set null (garment_id)`는 PG15+ 필요(로컬 PGlite 통과). 원격 push 전 PG 버전 확인.
- 매처 가중치·임계값은 근거 데이터 없는 기준값이다. 실제 품질로 쓰지 않는다.
- 새 오류 메시지를 만들지 않고 기존 매핑을 재사용했다(`garment_unavailable`→409 `OUTFIT_CONFLICT`, `invalid_feed_state`→409 `FEED_CONFLICT`). 전용 코드가 필요하면 `lib/supabase-user.js` 수정 필요.
- 동기 매칭이라 열린 작업 3개 제한(`mimic_open_limit`)·2시간 마감은 새 작업에 의미가 없다.
