# PRD 피드백

## 종합 의견

PRD는 `원샷 등록`, `추구미 추천`, `내 옷장으로 따라입기`라는 차별점을 명확히 보여줍니다. 반면 제품 비전, MVP, 기술 후보, KPI가 한 문서에서 모두 확정된 것처럼 섞여 있어 일정과 승인 기준이 과대 산정될 위험이 있습니다.

## 좋은 점

- 등록 피로를 원샷 CV로 해결한다는 문제-기술 연결이 분명합니다.
- 날씨 유틸리티에 추구미와 소셜 루프를 추가해 재방문 이유를 설명합니다.
- AI/BE/FE 역할과 주요 사용자 흐름이 연결되어 있습니다.
- 사용자가 AI 결과를 일괄 수정한다는 UX가 현실적입니다.

## 우선 수정할 부분

### 1. 제품 비전과 제출 MVP 분리

전체 소셜 기능과 실제 Styling Mimic은 로드맵으로 두고, 제출 MVP는 원샷 등록과 날씨·추구미·TPO 추천의 수직 흐름으로 제한하는 편이 좋습니다.

### 2. 추구미 수 통일

기존 문서는 15개, 최근 회의 메시지는 5개를 언급합니다. PRD 전 구간에서 하나로 통일해야 데이터, UI, API 스키마가 확정됩니다. MVP는 5개를 권장합니다.

### 3. TPO의 구현 수준 명시

TPO를 포함하되 수동 프리셋 + 룰 점수로 정의합니다. 캘린더 자동 해석과 별도 TPO 모델 학습은 P1 이후로 구분합니다.

### 4. 승인 지표를 재현 가능하게 수정

- `2초`: 업로드 제외/포함, 해상도, GPU, p50/p95 명시
- `90%`: Detection recall, mask IoU, category Macro F1 분리
- `에러 없이 렌더링`: 성공률과 제한 시간, 폴백 정의
- `매칭률 %`: 코사인 유사도와 사용자 표시 점수 분리

### 5. 모델명을 요구사항에서 분리

YOLO, SAM, Fashion-CLIP, Triton은 후보 기술입니다. PRD는 입력·출력·성능 요구를 정의하고 모델 선택은 기술 설계/실험 문서로 이동하는 것이 좋습니다.

### 6. 빈 옷장 상태 처리

온보딩에서 옷 등록을 건너뛸 수 있는데 홈은 내 옷 추천을 전제로 합니다. 최소 아이템 수, 샘플 코디 표시, 등록 재유도 중 하나를 명시해야 합니다.

### 7. 오전 7시 추천의 조건

사용자 시간대, 최신 위치 유효기간, 위치 권한 거부, 날씨 API 실패, 옷장 변경 후 재계산 정책이 필요합니다. MVP에서는 홈 진입 시 생성하고 이후 프리컴퓨팅을 추가하는 안이 더 단순합니다.

### 8. 소셜 운영 요구 추가

실제 커뮤니티를 MVP에 넣으면 공개 범위, 신고·차단, 이미지 권리, 삭제, 댓글 권한, 콘텐츠 모더레이션이 필수입니다. 이 항목이 없으면 소셜 기능은 샘플 피드로 제한해야 합니다.

### 9. 개인정보와 학습 동의 분리

위치 사용, 일정 접근, OOTD 공개, 업로드 이미지의 모델 개선 사용은 각각 별도 동의여야 합니다. 계정 삭제 시 원본·파생 이미지·임베딩·학습 후보 삭제 정책도 필요합니다.

## 권장 P0 사용자 스토리

> 사용자는 추구미 1~2개와 오늘의 TPO를 선택하고, 겹치지 않게 펼친 옷 2~6벌을 한 장으로 등록한다. AI가 나눈 아이템과 태그를 사용자가 수정·확정하면, 서비스는 현재 날씨에 부적절한 아이템을 제외하고 추구미와 TPO에 맞는 코디 3종을 제안한다. 사용자는 한 코디를 오늘 입기로 확정해 기록할 수 있다.

## 팀 피드백 요청 항목

1. 추구미 5개의 정확한 명칭과 선정 근거
2. TPO 5개 프리셋 동의 여부
3. 제출 범위를 M0 또는 M1 중 어디까지로 볼지
4. 소셜 피드를 실제 CRUD 또는 샘플 데이터 중 무엇으로 할지
5. 오전 7시 사전 생성이 반드시 필요한지
6. 2초·90% 목표의 테스트 장비와 지표 정의
