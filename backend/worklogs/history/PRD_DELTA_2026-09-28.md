# 마피코 최신 PRD 대비 기존 설계 차이

## 결론

기존 23경로 API/16테이블 SQL의 검증 통과는 최신 제품 요구사항 충족을 뜻하지 않는다. M0.5 축소안은 팀 승인 범위가 아닌 이전 에이전트 설계 제안이다. 이를 최신 PRD의 기준으로 강제하지 않는다.

| 항목 | 기존 설계 | 최신 요구/필요 변경 |
|---|---|---|
| 명칭 | MyFit:Core | 마피코. 역사 문서는 이력으로 유지 |
| 스타일 | 5종 이름 미정, seed 없음 | 페미닌/Y2K/미니멀/그런지/캐주얼 seed 필요 |
| 온보딩 | 선호 1~3개 저장 | 인지 분기·무드보드 선택/제안·대표/보조 데이터 추가 검토 |
| 인증 | 일반 Supabase JWT | 카카오 설정·동의·리다이렉트·신규/기존 회원 흐름 |
| TPO | 생략 시 프로필 기본값 적용 가능 | 홈 칩 삭제와 충돌. 기본값 자동 적용 여부 재결정 |
| 옷 상세 | 색상/추구미 등 속성 노출 | 누끼/원본/카테고리/선택 비고 중심. 내부 특징과 DTO 분리 |
| 코디 보관 | 추천 세트 중심 | 사용자 수동 조합과 날짜 없는 saved outfits 필요 |
| OOTD | 추천 채택으로만 생성 | 수동 조합/보관함/추천에서 생성, 착장샷·별점·메모 |
| 공개 피드 | 후속 제외 | 최신 제품 범위 포함. posts/likes/아카이브/공개권한 필요 |
| 따라입기 | 후속 제외 | 매칭 요청/결과/후보없음/보관함 연결 필요 |
| 통계 | 상세 계약 부족 | 착용 사실 기준 빈도/30일 미착용; 계획과 착용 구분 |
| 탈퇴 | DB cascade 중심 | Storage/공개 이미지/게시물/작업/학습후보 삭제 책임 필요 |
| 스케줄 | 7시 또는 온디맨드 | 최신 5시 메모, 날씨변화·수동갱신 규칙 재정의 |

## 사용자에게 먼저 확인할 질문 초안

아직 팀에 전송하지 않았다. 사용자의 1차 확인을 거친 뒤 팀 질문 문서로 확정한다.

1. TPO는 홈 입력만 없애나요, 이번 추천 로직에서도 빼나요?
2. 추천 생성은 새벽 5시인가요 오전 7시인가요? 옷이 부족하면 0~2개와 이유를 보여줘도 되나요?
3. 플랫폼은 모바일 웹 우선으로 진행하나요, 앱스토어 출시가 필요한 네이티브 앱인가요?
4. 코디 보관은 날짜 없이, 캘린더는 착용/예정으로 구분해도 되나요? 하루 여러 코디 허용 여부는요?
5. 색상·추구미는 화면에서만 숨기나요, AI 자동 태깅 자체도 제외하나요?
6. 전체 제품에 소셜/따라입기를 유지하되 데모 동결 전 품질 게이트를 두는 일정안에 동의하나요?
7. BE의 주당 실제 가용시간과 Supabase 개발용 프로젝트는 무엇인가요?

## API/DB 다음 수정 방향 — 아직 구현하지 않음

- `saved_outfits`/구성 아이템과 `ootd_entries`, 공개 `feed_posts`를 목적별로 분리한다.
- OOTD는 생성 시 옷/날씨 스냅샷 보존. 과거/미래 날짜와 오늘 날씨를 혼동하지 않는다.
- 게시물은 소유자 원본 Storage 경로를 공개하지 않고 공유 허용된 이미지와 정보만 투영한다.
- 사용자 선호의 대표/보조 순위와 무드보드 원본 선택은 설명 가능하게 저장하되 점수 산식은 합의 후 고정한다.
- 임베딩 모델·차원·버전 확정 전 임의 vector 차원을 SQL에 넣지 않는다.
- 새 API·마이그레이션 및 RLS 테스트를 함께 버전업한다. 현재 v0.2는 이전 설계로 표시한다.

## 배포 범위

현재 배포는 HTTP health/readiness/정적 카탈로그 검증뿐이다. Supabase 미연결 상태이며 기존 SQL을 원격에 적용하지 않았다. 상세 증거는 `WORK_SUMMARY_2026-09-28.md` 참조.
