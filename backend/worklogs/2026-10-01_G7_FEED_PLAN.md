# G7 피드·공유 미디어·좋아요 HTTP 수직 슬라이스 계획

상태: 로컬 구현·검토·검증 완료  
범위: feed 5개, 공유 media 2개, 좋아요 2개, 내 archive/list 2개 등 11개 operation  
예상 증가: G6 완료 기준 `implemented-local` 36/50 → G7 완료 47/50  
선행조건: G6 migration·HTTP 결과 회수와 G1~G6 전체 회귀 통과

## 1. bounded goal과 완료 기준

사용자가 비공개 게시물 초안을 만들고, closet 원본과 분리된 `feed-private` 공유 이미지를 업로드·검증한 뒤 명시적으로 공개하며, 현재 볼 수 있는 게시물에 좋아요/아카이브를 적용하는 전체 수직 흐름을 구현한다.

- feed: `listFeed`, `createFeedPost`, `getFeedPost`, `updateFeedPost`, `deleteFeedPost`.
- media: `createFeedMediaUpload`, `completeFeedMedia`.
- likes/lists: `likeFeedPost`, `unlikeFeedPost`, `listLikedPosts`, `listMyPosts`.

다음 증거가 모두 있을 때만 11개 operation을 `implemented-local`로 올린다.

1. private draft → 서버 생성 media 경로 → signed upload → 실제 bytes 검증 → public 전환이 runtime 경로와 SQL transaction으로 연결된다.
2. 공개 DTO에서 `source_ootd_id`, garment ID, closet object key, raw feed object key, 이메일/Auth metadata, 내부 DB 열이 나오지 않는다.
3. 공개/소유자 가시성, 삭제 즉시 숨김, 비공개 전환 후 archive 숨김과 신규 signed URL 차단을 SQL·HTTP 테스트가 함께 증명한다.
4. like/unlike는 동시·중복 요청에도 멱등이고 현재 볼 수 없는 다른 사용자의 post를 좋아요로 우회 조회할 수 없다.
5. feed/list/archive pagination과 필터가 안정적인 keyset 및 cursor binding을 사용한다.
6. 정본 OpenAPI·사본·coverage·설계문서·manifest와 G1~G7 회귀가 일치한다.

범위 밖은 댓글, 독립 스크랩, 여러 추구미 태그, OOTD 독립 사진, 구매 링크, 이미지 변환/리사이즈, 실제 Storage cleanup scheduler, 따라입기 결과 생성이다. G8 mimic은 공개 post를 소비하지만 G7에서 실행하지 않는다.

## 2. 현재 계약·DB 기준선과 보완점

- `feed_posts`는 nullable `source_ootd_id`, caption, aesthetic, 사용자 입력 weather tag/temperature, `private|public`, timestamps, soft-delete를 가진다.
- `feed_media`는 `feed-private` object key, position, verified/deleted 시각을 가지지만 업로드 검증에 필요한 `content_type`, `byte_size`가 없다. G7 additive migration에서 OpenAPI 정본과 같은 1 byte~20 MiB와 JPEG/PNG/WebP metadata를 추가한다.
- `post_likes(user_id,post_id)` PK가 중복 좋아요를 막는다. 기존 RLS는 본인의 좋아요 중 현재 RLS로 보이는 post만 읽게 한다.
- `feed-private` bucket은 private, 20 MiB, JPEG/PNG/WebP로 생성되어 있으나 브라우저 upload policy가 없다. 정확히 등록된 본인 미검증 media 경로에만 INSERT/검증 SELECT가 가능하도록 좁은 policy를 추가한다.
- `FeedPostCreate.weather_code`는 optional이지만 `FeedPost.weather_code`는 non-null required다. 생략 시 `unknown`으로 canonicalize한다. temperature는 DB 기준 -90..60을 OpenAPI와 handler validation에도 명시한다.
- `FeedPostCreate.aesthetic_id`는 필수지만 DB 열은 nullable이다. 신규 G7 write는 활성 aesthetic만 허용하고 non-null을 보장한다. 기존 불완전 row를 임의 backfill하거나 공개하지 않는다.
- `FeedPostPatch`에 version이 없으므로 이번 계약은 row lock을 쓰되 optimistic version 없는 last-write-wins다. version을 몰래 응답에 추가하지 않고 제한을 결과에 기록한다.

기존 migration은 수정하지 않는다. P1-G6-DB가 소유한 `202610010003_outfits_ootd.sql` 회수 뒤 root가 G7의 다음 충돌 없는 migration 순번을 확정한다.

## 3. privacy·권한·safe projection

### 가시성 행렬

| 대상 | public post | 본인 private post | 타인 private | deleted post |
|---|---|---|---|---|
| `/feed` | 표시 | 표시하지 않음 | 표시하지 않음 | 표시하지 않음 |
| 상세 | 표시 | 소유자에게 표시 | 404 | 404 |
| `/me/posts` | 본인 것 표시 | 본인 것 표시 | 해당 없음 | 표시하지 않음 |
| `/me/likes` | 내가 like한 것 표시 | 내가 like한 본인 post만 표시 가능 | 숨김 | 숨김 |
| 새 signed read URL | 발급 | 소유자에게만 발급 | 발급 금지 | 발급 금지 |
| like 추가 | 허용 | 본인 post면 허용 | 404 | 404 |

- 모든 handler는 Bearer JWT를 검증한다. create/update/media/like RPC는 `auth.uid()`를 사용하며 다른 user ID를 인자로 받지 않는다.
- `feed_posts` direct write, `feed_media` direct table 접근, `post_likes` direct write는 계속 차단한다. 공개 함수는 exact revoke/grant를 사용한다.
- 다른 사용자 profile은 일반 profiles RLS를 우회해 읽지 않는다. feed projection은 author의 `id`, nullable `display_name` 두 필드만 반환하는 좁은 DB projection을 사용한다.
- BFF 내부 projection이 media object key를 읽어야 하면 사용자 인증 뒤 server-only narrow RPC/gateway에서 visibility를 다시 검사한다. 내부 row/object key는 응답·로그·오류에 넣지 않고 signed URL로만 바꾼다.
- service-role projection을 사용할 경우 `p_actor_id`를 JWT 결과에서만 전달하고 함수가 public/private/deleted 조건을 자체 적용한다. 임의 테이블/정렬/필터 문자열을 받지 않는다.

### FeedPost DTO

- 허용 필드는 OpenAPI의 `id`, safe author, caption, aesthetic ID, 사용자 입력 weather tag/temperature, visibility, signed media, `liked_by_me`, `like_count`, created_at뿐이다.
- `source_ootd_id`, OOTD snapshot, garment IDs, closet-private 경로/URL, feed bucket/object key, media ID, verified metadata는 제외한다.
- weather tag는 사용자가 작성한 분류일 뿐 관측 사실 또는 G5 WeatherSnapshot이라고 표현하지 않는다.
- media는 position 순 verified+nondeleted row만 5분 signed read URL로 만든다. public post는 최소 한 개를 보장하고, private draft는 빈 배열이 가능하다.
- request-wide Storage signing 실패는 503으로 실패 폐쇄한다. path가 없거나 unverified/deleted인 row는 projection에서 제외하지만 public invariant가 깨져 media가 0개면 내부 무결성 오류로 처리하고 post를 공개 피드에 내보내지 않는다.
- private/delete 전에 발급한 URL은 만료 전까지 유효할 수 있다. 신규 발급은 상태 변경 transaction 완료 직후 차단한다.

## 4. 게시물 lifecycle

### private draft 생성

`create_my_feed_post(source_ootd_id,caption,aesthetic_id,weather_code,temperature_c,idempotency_key)` 형태의 authenticated RPC를 둔다.

1. body exact allowlist, caption 0~2,000자, active aesthetic, weather enum, nullable finite temperature -90..60, `visibility='private'`, idempotency key를 검증한다.
2. `weather_code` 생략은 `unknown`, temperature 생략은 null로 canonicalize해 request hash를 만든다.
3. `source_ootd_id`가 non-null이면 본인의 nondeleted G6 OOTD인지 확인한다. null인 gallery post도 허용한다. OOTD의 garment/snapshot을 post row에 복사하거나 외부 DTO에 노출하지 않는다.
4. post와 operation별 idempotency response를 한 transaction에서 저장한다. 같은 key·같은 hash는 기존 201 private post를 재생하고 다른 hash는 409다.
5. 생성만으로 공개하거나 OOTD를 변경하지 않는다.

### 상세·수정·공개/비공개 전환

- 상세는 public 또는 owner private만 반환하고 deleted/타인 private는 404다.
- update RPC는 owner post를 `FOR UPDATE`하고 caption/aesthetic/visibility presence flag를 적용한다. aesthetic은 active여야 하며 source OOTD와 weather fields는 patch 대상이 아니다.
- `private→public`은 같은 transaction에서 verified+nondeleted media가 1개 이상인지 검사한 뒤에만 허용한다. pending/invalid media만 있으면 409 `FEED_MEDIA_REQUIRED`다.
- `public→private`은 즉시 허용한다. feed와 타인의 상세·liked archive·G8 신규 mimic에서 사라지고 신규 signed URL 발급이 중단된다. likes와 verified media row는 보존해 재공개가 가능하다.
- 같은 visibility로의 patch도 안전해야 하나, version 없는 동시 caption update는 last-write-wins임을 숨기지 않는다.

### 철회/삭제

`delete_my_feed_post(post_id)`는 owner row를 잠그고 `deleted_at=now()`, `visibility='private'`, `source_ootd_id=null`, 연결 media의 `deleted_at` cleanup marker를 한 transaction에서 기록해 202 `{id,status:'deletion_pending'}`를 반환한다.

- 첫 성공과 같은 소유자의 재호출은 같은 202를 반환해 네트워크 재시도에 안전하게 한다. 타인/존재하지 않는 ID는 404다.
- post_like와 향후 mimic row를 응답에서 즉시 숨기지만 요청 이력 보존을 위해 이 transaction에서 임의 hard-delete하지 않는다.
- feed Storage 객체 실제 삭제는 marker를 소비하는 server-only cleanup 작업의 책임이다. G7 HTTP 완료는 즉시 비노출과 durable cleanup marker까지이며 hosted scheduler 실행은 미검증으로 남긴다.
- 이미 발급된 signed URL은 TTL까지 유효할 수 있음을 사용자 삭제 안내와 결과 문서에 적는다.

## 5. feed-private signed upload와 실제 bytes 검증

### media 예약·서명

`create_my_feed_media(post_id,content_type,file_size,idempotency_key)` RPC가 다음을 원자 처리한다.

1. post가 본인 소유, nondeleted, private인지 잠그고 검사한다. public post에 media를 추가하려면 먼저 private 전환한다.
2. MIME은 JPEG/PNG/WebP, 크기는 OpenAPI 정본 기준 1 byte~20 MiB다. 남용 방지를 위해 post당 최대 10개로 고정하고 OpenAPI 설명과 SQL 상수를 일치시킨다.
3. media UUID와 `${userId}/${postId}/${mediaId}.${ext}` object key를 서버에서 생성하고 input 순서와 무관하게 다음 position을 row lock 아래 배정한다. 클라이언트 path/position/upsert를 받지 않는다.
4. feed_media row와 idempotency 201 response를 저장한다. 같은 key replay는 같은 media ID/path를 내부 반환해 새 signed URL을 다시 발급할 수 있고 다른 body는 409다.
5. BFF는 G3의 검증된 `createSignedUpload` 경로를 재사용해 user JWT로 non-upsert PUT URL과 정확한 `Content-Type` header, 만료시각만 반환한다. raw object key는 FeedMediaUpload DTO에 넣지 않는다.

Storage INSERT policy는 `feed-private`, 첫 path segment=`auth.uid()`, 정확한 owner media row, private+nondeleted owner post, `verified_at is null`, media `deleted_at is null`을 모두 요구한다. verification ranged GET용 SELECT도 같은 미검증 row에만 제한한다. UPDATE/DELETE/upsert 또는 사용자 prefix 전체 쓰기는 허용하지 않는다.

### complete-upload

1. postId/mediaId/idempotency를 검증하고 owner private post와 정확한 media mapping을 읽는다.
2. user JWT로 object의 선두 최대 64 KiB ranged GET을 수행한다. object 없음은 retry 가능한 409 `UPLOAD_NOT_FOUND`다.
3. 응답 MIME, Content-Range의 전체 크기, 등록 크기, JPEG/PNG/WebP magic bytes와 가능한 최소 decode/header 구조를 검증한다. metadata만 믿지 않는다.
4. `complete_my_feed_media` RPC가 `storage.objects`의 bucket/name/owner/size/MIME를 독립 검증하고, valid면 `verified_at`을 한 번 설정한다. invalid면 media `deleted_at` marker와 idempotency 422를 원자 기록하며 post는 private로 유지한다.
5. 같은 key·같은 media completion은 기존 200/422를 재생하고 key 재사용 충돌은 409다. 이미 검증된 media의 올바른 replay는 200이다.
6. 업로드 완료 자체는 public 전환이 아니다. 성공 뒤에도 별도 PATCH가 필요하며 response는 현재 private FeedPost safe DTO다.

signed-upload URL 형식, Range 응답, Storage owner metadata, image decoding의 실제 hosted 동작은 로컬 mock 통과와 별개로 기록한다.

## 6. 좋아요와 아카이브

### like/unlike RPC

- `like_my_feed_post(post_id)`는 현재 public 또는 본인 private이고 nondeleted인 post만 허용한다. 타인 private/deleted/missing은 동일한 404다.
- `(user_id,post_id)` insert는 `ON CONFLICT DO NOTHING`으로 처리해 중복·동시 PUT 모두 204다. 자신의 post 좋아요도 현재 계약상 허용한다.
- `unlike_my_feed_post(post_id)`는 본인 like row가 있으면 post가 이후 private/deleted가 되었어도 삭제할 수 있어야 한다. 이는 숨은 archive를 정리하기 위한 예외이며 post 내용은 반환하지 않는다.
- DELETE는 like row가 없어도 204다. 보이지 않는 post의 존재 여부를 404 차이로 노출하지 않도록 valid UUID/auth 요청에는 멱등 204를 우선한다. OpenAPI의 404 사용 여부는 검토에서 명시적으로 정합화한다.
- like_count는 현재 post의 like row 수, liked_by_me는 actor의 존재 여부다. 두 값은 같은 projection query/snapshot에서 계산해 목록/상세가 불필요하게 어긋나지 않게 한다.

### `/me/likes`

- 현재 actor가 like했고 현재 볼 수 있는 nondeleted post만 반환한다. 다른 사용자가 private로 전환하거나 삭제한 post는 archive에서 즉시 사라진다.
- 정렬은 archive 의미에 맞춰 `post_likes.created_at DESC,post_id DESC`로 문서화한다. FeedPost의 `created_at`은 post 작성 시각이며 cursor의 like 시각은 외부 DTO에 추가하지 않는다.
- unlike 후 다시 like하면 새 like 시각으로 archive 앞에 나타난다.

## 7. 목록·필터·cursor

- `/feed`: public+nondeleted만 `feed_posts.created_at DESC,id DESC`. `aesthetic_id`, weather code, temperature `[min,max)` 필터를 적용한다.
- `/me/posts`: 본인 nondeleted private/public을 `created_at DESC,id DESC`로 반환한다.
- `/me/likes`: 위에서 정한 like 시각 keyset을 사용하고 현재 visibility를 매 페이지 재검사한다.
- 모든 목록은 limit 1~100, 기본 20, limit+1 방식이다. cursor에는 schema/endpoint version, 마지막 정렬 원시값+UUID, 필터 canonical 값이 포함된다.
- 다른 endpoint·다른 filter의 cursor, 1,024자 초과, malformed base64/JSON, 잘못된 timestamp/UUID는 upstream 호출 전 400이다.
- temperature는 유한수, DB 범위 -90..60, `min<max`; 하한 포함/상한 제외다. aesthetic UUID가 비활성이면 빈 결과 또는 422 중 하나를 검토에서 고정하며 타 사용자 데이터 유무를 드러내지 않는다.
- 페이지 사이 visibility/delete/like 변경은 snapshot isolation을 약속하지 않는다. keyset은 중복/역주행을 막되 사라진 row는 다음 페이지에서 제외한다.

## 8. G6 OOTD·G8 mimic 충돌 경계

### G6 OOTD

- source OOTD는 생성 시 본인 소유만 확인하고 FeedPost DTO에는 절대 노출하지 않는다. gallery post는 source null이다.
- G6의 OOTD delete RPC는 nondeleted feed reference가 있으면 409 `OOTD_IN_USE`로 막는다. 사용자는 G7 post 철회를 먼저 수행한다.
- G7 철회 transaction이 `source_ootd_id`를 null로 분리해 이후 OOTD hard-delete를 허용한다. G6가 먼저 삭제를 시도하면 nondeleted feed reference 때문에 409이고, 철회 후 재시도하면 성공해야 한다. root는 두 migration의 lock 순서를 맞춘다.
- OOTD 수정/삭제가 이미 복사된 feed media, caption, tags를 자동 변경하지 않는다. closet-private 이미지를 feed URL로 직접 재사용하지 않는다.

### G8 mimic

- G8 create/get은 매번 source post가 public+nondeleted인지 재검사한다. G7 private/delete 전환 뒤 신규 mimic과 기존 결과 재노출을 막을 수 있어야 한다.
- G7 projection은 G8에 raw OOTD/garment IDs를 제공하지 않는다. G8 worker가 사용할 서버 내부 media access는 별도 server-only 계약이다.
- post delete는 mimic row를 즉시 hard-delete하지 않고 visibility gate로 숨긴다. 계정 삭제 cascade와 cleanup은 G8/G9 회귀에서 검증한다.

## 9. migration·runtime 예정 단위

root 구현 시 다음 단위로 최소 변경한다.

- additive G7 migration: feed_media MIME/size, 필요 index, feed create/update/delete, media create/complete, like/unlike narrow RPC, feed visibility/projection helper, Storage exact policies.
- SQL assertion: direct write 차단, safe column grants, cross-owner/source/media, private/public/delete, like archive RLS, Storage path/metadata.
- feed domain module: strict input, keyset cursors, safe DTO, author/like aggregation.
- feed media module: G3 signed upload/ranged read reuse, magic/size/MIME 검증, batch signed read URLs.
- 11개 handlers 및 unit/contract fixture.
- OpenAPI 정본/사본, API/DB design, coverage registry, export manifest, G7 result worklog.

server-only projection/helper를 만들면 arbitrary SQL/table/path를 받지 않고 exact RPC allowlist에만 추가한다. 실제 비밀값을 새로 만들거나 출력하지 않는다.

## 10. SQL·HTTP 테스트 계획

### 게시물·privacy

- create exact allowlist, caption 0/2,000/2,001, aesthetic active/inactive, weather default unknown, temperature 경계, private 외 visibility 거절.
- source OOTD 본인/null 성공, 타인/없는 ID 404, source가 DTO·로그에 없음.
- create idempotency replay/conflict/expiry와 post+response 원자 rollback.
- public 전환은 verified media 1개 이상, private 전환 즉시 public feed/detail/liked archive/new sign 차단, 재공개 가능.
- update owner-only, aesthetic validation, version 없는 last-write-wins 문서 일치.
- delete 202 replay, 즉시 목록/상세 숨김, media marker, likes/mimic visibility, 기존 signed URL TTL 경계.
- FeedPost JSON 정적 검사로 OOTD ID, garment ID, closet/feed object key, email/Auth metadata 비노출.

### Storage/media

- MIME/size 경계, 최대 media 수, 서버 생성 canonical path/position, create idempotency와 expired URL 재서명.
- 타인 post/media, public/deleted post, 임의 path/position, upsert, broad prefix upload 차단.
- signed upload host/path 검증과 secret/token 오류 비노출.
- object 없음 409 retryable; MIME/size/magic/Content-Range 불일치 422+cleanup marker; valid 200+verified_at.
- completion replay/conflict, mediaId가 다른 post에 속한 경우 404, 업로드 완료가 자동 public로 바뀌지 않음.
- unverified/deleted media signed read 금지, verified media position ordering, signing 장애 503.

### 좋아요·pagination

- public/own private like, 타인 private/deleted like 404, 중복·동시 PUT 204 한 row.
- visible/hidden/deleted post unlike와 없는 like DELETE가 privacy-safe 204.
- private/delete 전환 뒤 타인의 `/me/likes`에서 즉시 제외되지만 underlying archive row 정책이 우회 조회를 허용하지 않음.
- like_count/liked_by_me 목록·상세 일치, 타 사용자 like identity 비노출.
- feed/my/likes 각각 안정 정렬, limit 1·100, next cursor, filter binding, malformed cursor, 온도 `[min,max)` 경계.

### SQL/RLS·회귀

- anon/authenticated direct table writes와 feed_media direct select 실패, exact RPC만 실행 가능.
- service-role projection도 actor/visibility를 재검증하고 타인 private/deleted raw row를 반환하지 않음.
- Storage INSERT/SELECT policy가 owner+exact media+private+unverified 조건을 모두 요구하고 UPDATE/DELETE는 없음.
- G6 feed-reference OOTD delete 409→post 철회/source detach→재시도 성공 흐름.
- G8가 private/deleted post를 입력으로 사용할 수 없는 visibility 회귀.

G7 종료 시 `npm test`, `npm run test:schema`, `npm run coverage:contract`, `npm run seed:validate`, `npm run smoke:preview`, `git diff --check`를 모두 실행하고 operation registry가 정확히 47/50인지 확인한다.

## 11. 오류·fallback 정책

| 상황 | 결과 |
|---|---|
| 인증 없음/잘못된 JWT | 401 |
| malformed body/query/path/cursor | 400 |
| MIME/크기/태그/온도/필터 정책 위반 | 422 |

## 12. hosted 미검증과 사용자 Supabase 후속 설정

로컬 완료 뒤에도 다음은 별도 hosted 검증으로 남긴다.

- 실제 Supabase Storage signed upload, Range, owner/metadata, RLS policy, URL 만료와 private/delete 직후 신규 sign 차단.
- concurrent media position/idempotency, public 전환/complete race, like count/visibility race.
- Preview의 author projection, batch signed URL, cursor pagination, G6 OOTD 삭제와 G8 mimic visibility E2E.
- cleanup marker 이후 실제 Storage object 삭제 scheduler. 202는 즉시 접근권 제거와 cleanup 접수를 뜻하며 물리 삭제 완료를 뜻하지 않는다.

사용자가 수행할 설정은 다음으로 제한한다.

1. G6 다음 순번의 G7 migration을 개발 Supabase에 적용한다.
2. `feed-private` bucket이 private, 20 MiB, JPEG/PNG/WebP인지 확인한다.
3. Dashboard에서 public bucket 전환, broad INSERT/SELECT, UPDATE/DELETE/upsert policy를 추가하지 않는다.
4. 기존 서버 Supabase URL/publishable key와 server-only secret을 유지한다. G7 전용 신규 외부 API key는 필요 없다.
5. 사용자 A/B로 private post 격리, signed upload/complete/public 전환, like/archive, private/delete URL 재발급 차단을 hosted에서 확인한다.
6. Storage cleanup scheduler를 나중에 연결할 때 marker 소비 성공 후에만 object를 지우고 실패 재시도·로그에 path/token을 남기지 않는다.

원격 DB·배포·비밀값·Dashboard policy는 이 bounded goal에서 변경하지 않는다.

## 13. 구현 순서와 중단 조건

1. G6 DB/HTTP 결과와 `source_ootd_id` 삭제 lock/source detach 규칙을 회수한다.
2. read-only 검토에서 server-only projection, post당 media 상한, unlike privacy, G8 visibility를 확정한다.
3. additive migration+SQL assertion으로 visibility, write RPC, Storage policy를 먼저 고정한다.
4. private post CRUD와 safe projection/author/like aggregation을 구현한다.
5. feed-private upload/complete/read signing을 G3 adapter 재사용으로 구현한다.
6. like/unlike와 feed/my/likes keyset pagination을 구현한다.
7. G6 OOTD reference와 G8 visibility 회귀를 추가한다.
8. fixture/OpenAPI/coverage/설계/manifest/result worklog을 동기화하고 G1~G7 전체 gate를 실행한다.

타인 private row 또는 원본 경로 유출, public media invariant 위반, broad Storage policy, mock-only upload, G6 OOTD 삭제 불능, SQL/회귀 실패, 정본/사본 불일치 중 하나라도 있으면 G7을 완료 처리하지 않고 checkpoint와 정확한 재개 지점을 남긴다.
