## 한눈에 보는 현재 상태

| 영역 | 결과 | 남은 일 |
|---|---|---|
| 시각자료 | 유저플로우·아키텍처·기능맵·ERD 총 16개 완성 | 팀 내용·표현 최종 검토 |
| 공유 이미지 | PNG 16개, SVG 16개, 형식별 ZIP 제공 | 필요한 이미지를 팀 채널에 사용자가 직접 공유 |
| API 계약 | OpenAPI 50개 operation 정의, Swagger 사본 동기화 확인 | 계약 변경 시 정본과 Swagger 사본 동시 갱신 |
| 백엔드 | 49/50 operation `implemented-local` | `requestAccountDeletion` 구현 |
| 데이터베이스 | migration 12개, public 테이블 24개, 실제 FK 44개를 로컬 카탈로그에서 확인 | hosted Supabase 적용·RLS·동시성 E2E |
| 외부 연동 | Auth·Storage·AI worker·날씨 공급자 경계 설계 및 로컬 계약 검증 | 실제 서비스 자격증명과 배포 환경에서 통합 검증 |

`implemented-local`은 HTTP·SQL·계약 테스트의 로컬 구현 상태다. 프론트엔드 화면, 실제 AI 추론, hosted Supabase 또는 제품 배포 완료를 뜻하지 않는다.

## 이번 시각자료에 포함된 내용

1. 사용자 여정 6개: 전체 여정, 로그인·온보딩, 옷 등록·분석, 날씨·추천, 보관함·OOTD, 피드·따라입기.
2. 시스템 구조 4개: 신뢰 경계, 분석 callback, 따라입기 callback, 현재 추천과 향후 AI 설명 구조.
3. 기능맵 1개: PRD 기능 ID 32개와 OpenAPI operationId 50개의 대응.
4. 데이터베이스 5개: DB 전체 업무 흐름과 계정·취향, 등록·분석, 추천·OOTD, 피드·따라입기 상세 ERD.

로그인 흐름에는 온보딩 완료 사용자의 홈 직행을 포함했다. 분석 부분 성공은 성공한 결과를 유지하면서 부족분을 새 배치로 보완하는 흐름으로 표현했다.

## ERD 검토에서 확인한 핵심

- ERD는 migration 12개를 일회용 PGlite에 적용한 뒤 PostgreSQL 카탈로그에서 public 테이블 24개와 FK 44개를 읽어 생성했다.
- `mimic_source_items.feed_media_id`, `mimic_candidate_items.garment_id`, `asset_id`는 식별자를 저장하지만 실제 FK가 아니다. `job_id`만 `mimic_requests`를 참조한다.
- `ootd_entries.item_snapshot`은 기록 당시 의류를 보존하는 JSON이며 의류별 FK 테이블이 아니다.
- 개인 옷장 이미지는 `garment_assets`, 공개 공유 이미지는 `feed_media`로 분리한다. DB 행 삭제만으로 Storage 객체가 자동 삭제되지는 않는다.
- ERD의 실선은 식별 관계, 점선은 비식별 FK다. DB 전체 흐름도의 화살표는 업무 흐름이며 FK를 뜻하지 않는다.

## 검증 결과

- `npm ci` 후 `npm run all`로 ERD 생성 → Mermaid 렌더 → PNG/SVG 내보내기 성공.
- 브라우저 렌더 도식 16개, Markdown 상대 링크 73개 확인.
- 공유 PNG와 SVG 각각 16개, ZIP 엔트리도 각각 16개 확인.
- PNG 최소 폭 1,920px, 도식 경계 잘림 검사 통과.
- 390px 화면에서 문서 전체 가로 넘침 없음. 넓은 도식과 표는 자체 스크롤 사용.
- Swagger `sync:check` 통과. 정본과 Swagger 사본 SHA-256 일치.
- 2026-10-09 확인 시 작업 트리 깨끗함. 2026-10-02 시각자료 커밋 이후 새 로컬 변경 없음.

백엔드 98개 테스트는 기존 G8 결과 기록이다. 이번 리포트 작성 시 백엔드 전체 테스트나 hosted E2E를 다시 실행하지 않았다.

## 팀 검토가 필요한 결정

- 최종 추구미 5종의 이름·정의·대표 이미지와 탐색 방식.
- TPO를 추천 로직에 유지할지 여부.
- 위치 권한 거절 또는 날씨 공급자 실패 시 사용자 경험.
- 하루 OOTD 개수, `wear_status`, 보관함의 화면 위치.
- 자유 형식 LLM 설명의 도입 여부와 평가 기준.
- 계정 탈퇴 시 DB·Storage·공개 게시물·AI 파생 데이터의 파기 순서.

## 다음 실행 순서

1. 팀은 [전체 검토본](index.html)에서 흐름과 표현을 검토한다.
2. 팀 채널에는 먼저 `01 전체 사용자 여정`, `11 전체 기능맵`, `12 DB 전체 흐름`을 공유한다.
3. 영역별 논의 시 02~10 및 13~16 상세 이미지를 추가한다.
4. 결정된 내용은 PRD 또는 의사결정 기록에 반영한 뒤 시각자료를 재생성한다.
5. 백엔드는 계정 탈퇴 구현과 hosted Supabase·Storage·AI worker·날씨 공급자 E2E를 별도 작업으로 진행한다.
